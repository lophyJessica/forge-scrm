# 姐夫新媒体运营系统：阶段性选型建议

> 建议日期：2026-08-23
> 决策状态：阶段性建议，尚未拍板
> 前置条件：LisaHost VPS 目标 4C + 4G + 80G，但升级尚未完成。

## 1. 决策原则

1. 不因平台热门或功能多而选择；以真实流程、维护人、数据源和资源为准。
2. 当前 Make MVP 已跑通，应利用其验证价值，不为“换平台”立即重做。
3. 自建系统拥有业务数据、状态、权限、提示词、引用、审核和操作记录。
4. 自动化平台通过后端 API 工作，不直接写 MySQL。
5. DeepSeek 输出必须经后端 Schema 校验、重试和审核。
6. 自动化平台必须可逐步替换，不能成为唯一事实源。

## 3. 五个方案的阶段判断

### 3.1 方案 1：自建运营系统 + Make + DeepSeek + MySQL

- **短期**：最合适。保留已验证流程，把新增投资放在业务后台和 API。
- **长期**：Make 只保留通知、外部 SaaS 连接、临时流程和少量定时任务。
- **主要代价**：持续信用费用、双平台维护、迁移期数据同步。
- **不解决**：Make 本身不解决业务版本、引用、状态和审计。
- **不应选择的情况**：云端执行或数据跨境不可接受，或月调用量导致信用成本不可控。

### 3.2 方案 2：自建运营系统 + n8n 自托管 + DeepSeek + MySQL

- **短期**：不应为了替换而立即重建两条 Make 场景。
- **中期**：最值得做 VPS 最小验证，优先测试 Webhook、定时、HTTP、DeepSeek、日志和备份。
- **长期**：适合作为可替换编排层，不作为业务状态核心。
- **主要代价**：升级、安全、备份和 PostgreSQL/Redis 运维；部分治理能力付费。
- **不解决**：业务幂等、提示词版本、资料引用和审核仍需后端。
- **不应选择的情况**：无人能维护容器和安全，或 4G 实测没有足够余量。

### 3.3 方案 3：自建运营系统 + Activepieces 自托管 + DeepSeek + MySQL

- **短期**：可作为非技术可用性试验，不宜直接按完整生产拓扑落地。
- **中期**：只有在姐夫需要直接编辑流程、且单容器低频实测稳定时继续评估。
- **长期**：若需要官方生产拓扑，应准备独立数据库/Redis/S3 和更多内存。
- **主要代价**：生产资源高；Git Sync、审计、密钥治理等受套餐限制。
- **不解决**：飞书原生 Piece 未确认，复杂采集仍需要代码。
- **不应选择的情况**：必须把全部组件压在 4G VPS，或需要低成本完整企业治理。

### 3.4 方案 4：自建运营系统 + Windmill 或 Node-RED + DeepSeek + MySQL

Windmill 变体：

- 适合开发者维护的复杂采集、脚本、队列和数据处理；
- 需要 PostgreSQL 和 worker，资源与运维高于表面；
- 不适合姐夫直接配置复杂流程。

Node-RED 变体：

- 适合轻量 HTTP、事件和少量 JavaScript Flow；
- 资源可能较低，但官方未给出本项目可直接采用的最低基线；
- durable queue、细粒度权限、审计和执行追溯不足。

共同结论：方案 4 不作为当前主路线。Windmill 可在“复杂采集”需求成立后专项验证；Node-RED 可用于轻量边缘流程，不作为长期核心。

### 3.5 方案 5：自建运营系统 + 后端任务调度/队列 + DeepSeek + MySQL

- **短期**：不适合从第一天一次性全自建，会延迟业务验证。
- **中期**：从一个核心任务开始，例如结构化分析或抖音采集，建立幂等、重试和任务日志。
- **长期**：最适合作为业务核心，自动化平台退到外围。
- **主要代价**：开发、测试、监控、告警、凭据、扩容和灾备全部由团队负责。
- **不解决**：不会自动获得低代码连接器生态；每个第三方接入都要维护。
- **不应选择的情况**：没有稳定开发维护人，或一期时间要求极紧且业务流程尚未验证。

## 4. 十类阶段性建议

### 4.1 当前 MVP 最适合的方案

- **推荐方案**：方案 1，保留 Make 两条现有场景。
- **推荐理由**：已经真实跑通，替换不会增加业务验证价值。
- **主要代价**：继续产生 Make 信用费用和双系统过渡成本。
- **暂不解决**：Make 的长期锁定和复杂场景维护。
- **不应该选它的情况**：现有运行已不稳定、成本已不可接受或云端执行不合规。

### 4.2 VPS 自托管最适合的方案

- **推荐方案**：先验证方案 2 的 n8n 单实例，不启用 queue mode。
- **推荐理由**：自托管、Webhook、HTTP、DeepSeek/MySQL 原生节点和执行日志最均衡。
- **主要代价**：需要容器、安全、备份和后续 PostgreSQL/Redis 规划。
- **暂不解决**：4G 是否能同时承载 API、MySQL、Nginx 和 n8n。
- **不应该选它的情况**：VPS 实测余量不足或无人负责运维。

### 4.3 最适合非技术用户维护的方案

- **推荐方案**：短期 Make；中期比较 Make 与 Activepieces 的真实任务可用性。
- **推荐理由**：Make 已有姐夫入口；Activepieces 的可视化和 AI Piece 值得测试。
- **主要代价**：平台逻辑仍需要技术人员治理，Activepieces 生产资源和高级套餐成本较高。
- **暂不解决**：姐夫是否真的需要编辑流程，而不是只使用后台按钮。
- **不应该选它的情况**：姐夫只操作自建后台，无需接触自动化编辑器。

### 4.4 最适合复杂采集的方案

- **推荐方案**：长期方案 5；Windmill 作为开发者采集平台备选。
- **推荐理由**：复杂分页、断点、幂等、签名、去重和测试更适合代码与任务队列。
- **主要代价**：开发和运维最高；Windmill 还需要 PostgreSQL。
- **暂不解决**：目标来源是否有官方 API 和合法授权。
- **不应该选它的情况**：只是少量、低频、单页 API，Make/n8n 已足够。

### 4.5 最适合 AI 内容生成的方案

- **推荐方案**：短期 Make；长期后端直接调用 DeepSeek。
- **推荐理由**：当前 Make 已跑通，长期后端更容易保存提示词版本、资料快照和结果引用。
- **主要代价**：后端需要实现异步、超时、重试和模型升级兼容。
- **暂不解决**：选题/脚本最终业务规则仍待姐夫确认。
- **不应该选它的情况**：后端尚无任务基础设施且只需低频 MVP。

### 4.6 最适合结构化数据分析的方案

- **推荐方案**：方案 5；自动化平台只负责触发和通知。
- **推荐理由**：DeepSeek 只保证有效 JSON，字段完整性、Schema、版本、人工修正和回写必须靠业务后端。
- **主要代价**：需要开发校验器、任务状态、原始响应和审核流程。
- **暂不解决**：分析任务和输出字段尚未确认。
- **不应该选它的情况**：只做一次性探索性分析，不需要长期结构化保存。

### 4.7 最适合作为长期核心的方案

- **推荐方案**：方案 5，自建后端任务队列；自动化平台保持可替换。
- **推荐理由**：业务数据、状态、版本、审计和幂等可以保持一致，不依赖某个平台画布。
- **主要代价**：最高的工程和运维责任。
- **暂不解决**：外围连接器仍可能需要 n8n/Make 等平台。
- **不应该选它的情况**：没有长期开发维护能力。

### 4.8 最不建议使用的方案

- **推荐排除**：不建议把 Node-RED 或 Pipedream 作为长期业务核心。
- **推荐理由**：Node-RED 的 durable queue、审计和业务追溯不足；Pipedream 核心不自托管且云端锁定较强。
- **主要代价**：排除后可能放弃 Node-RED 的轻量和 Pipedream 的免运维优势。
- **暂不解决**：二者仍可作为局部工具。
- **什么时候可以选**：Node-RED 用于轻量事件流；Pipedream 用于明确接受云端托管的快速集成。

### 4.9 推荐的混合架构

- **推荐方案**：短期“自建后台/API + Make 过渡”；中期“后端核心 + n8n 试点 + Make 存量”；长期“后端队列核心 + 一个可替换低代码平台”。
- **推荐理由**：降低一次性迁移风险，同时逐步收回业务事实和核心任务。
- **主要代价**：过渡期需要同时维护两个执行层和一致的任务追踪。
- **暂不解决**：最终低代码平台要等 VPS 和业务实测。
- **不应该选它的情况**：团队无法接受任何双轨期，此时应缩小范围再单线迁移。

### 4.10 从当前 Make MVP 迁移的路线

- **推荐方案**：先解耦数据目标，再迁移执行器。
- **推荐理由**：只要 Make 和未来平台都调用同一后端 API，执行器可逐条替换。
- **主要代价**：必须先建设最小后端任务接口和迁移校验。
- **暂不解决**：旧飞书数据如何迁移、保留多久。
- **不应该选它的情况**：当前还没有确定业务记录和任务的最小字段，此时先完成需求确认。

## 5. 推荐的迁移路线

### 阶段 0：保持现状

- 不修改 Make 场景；
- 记录每月运行量、失败率、credits、人工修复时间；
- 收回 `01-需求调研问题清单.md` 的关键答案。

### 阶段 1：建立后端事实入口

- 定义选题任务、脚本任务、资料和分析任务的最小 API 契约；
- 后端生成任务 ID、幂等键和状态；
- Make 后续只调用 API，不直接写 MySQL；
- 飞书继续接收通知或过渡副本。

### 阶段 2：迁移 AI 核心

- 后端固化提示词版本、资料快照、引用关系和模型参数；
- 先迁移结构化分析，再迁移选题和脚本中的一个；
- DeepSeek 输出统一经 Schema 校验和有限重试。

### 阶段 3：验证替代执行器

- VPS 升级后只安装一个候选做隔离验证，优先 n8n；
- 用一个无业务破坏的定时采集或通知 Flow 比较日志、重试、备份和维护；
- 同一任务用后端队列做对照，记录资源和开发时间。

### 阶段 4：逐条替换 Make

- 每次只迁移一个场景；
- 保留回退开关和对账期；
- 结果一致且运行稳定后再停用对应 Make 场景；
- 最终是否完全移除 Make 由实际成本和维护数据决定。

## 6. Make 的保留与替换边界

建议保留：

- 已跑通且仍低频稳定的选题/脚本场景；
- 飞书通知、邮件、Webhook 等外围集成；
- 临时运营流程和一次性编排。

建议逐步替换：

- 直接保存核心业务结果；
- 提示词版本和资料引用；
- 选题/脚本/分析状态机；
- 复杂采集、幂等、去重和断点；
- JSON Schema 校验和人工修正；
- 权限、审计和操作记录。

## 7. 关键风险

- VPS 4G 内存同时承载 API、MySQL、Nginx、对象存储连接和自托管自动化平台可能没有足够余量；
- n8n、Activepieces、Windmill 的生产模式可能引入 PostgreSQL 和/或 Redis，形成 MySQL 之外的额外状态组件；
- 国内内容平台 API 的账号类型、scope、企业认证、审核和地域限制可能阻断自动采集；
- 非官方爬取存在封号、接口变更、隐私和合规风险；
- 自动化画布内保存业务规则会导致版本、测试和迁移困难；
- AI 返回有效 JSON 不代表字段正确，空内容和截断仍需处理；
- 过渡期 Make、飞书、自建系统并存会产生重复写入和对账问题；
- 自建队列若缺少监控、死信、幂等和恢复演练，风险可能高于使用成熟平台。

## 8. 仍需姐夫或用户确认的问题

优先只确认三个会改变选型的问题：

1. 姐夫是否要亲自编辑自动化流程；如果不需要，非技术流程编辑器的权重应大幅降低。
2. 一期唯一优先目标是什么，以及真实任务频率、单次数据量和可接受失败恢复时间。
3. 视频号、小红书等无普通内容指标官方 API 时，是否接受手工/CSV 兜底及可接受期限。

还需用户在实施前拍板：一期/二期边界、自动化运维责任人、云端数据可接受性、月度成本上限和最终验收人。

## 9. LisaHost VPS 升级后必须验证

- `nproc`、可用内存、磁盘、Swap、网络、操作系统和 Docker 条件；
- API + MySQL + Nginx 的空闲及峰值资源基线；
- n8n 单实例空闲、单任务和并发任务资源；
- 是否有余量增加 PostgreSQL/Redis；
- Activepieces 单容器和 Windmill 最小部署的内存峰值，仅作为对照，不同时常驻；
- 日志增长、备份时间、恢复时间和磁盘占用；
- DeepSeek、飞书、抖音开放平台从 VPS 的网络可达性、延迟和错误率；
- 容器重启、任务重试、重复提交和断网恢复；
- 对象存储上传下载和大 CSV/TXT 导入；
- 安全更新、凭据轮换和最小权限。

验证前不假设 VPS 已升级，也不据 4C + 4G + 80G 纸面配置作最终安装决定。

## 10. 当前阶段结论

当前可执行但未拍板的路线是：

```text
短期：保留 Make MVP，先建设自建系统的业务 API 和事实层
中期：在升级后的 VPS 上优先验证 n8n 单实例，同时迁移一个核心任务到后端队列
长期：自建后端任务队列成为核心，低代码平台只负责可替换的外围编排
```

该路线仍需姐夫业务回答、VPS 实测和账号 API 真实申请结果共同验证。本轮未安装、部署、迁移或修改任何现有系统。
