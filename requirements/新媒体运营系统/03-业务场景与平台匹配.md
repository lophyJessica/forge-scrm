# 姐夫新媒体运营系统：业务场景与平台匹配

> 分析日期：2026-08-23
> 结论性质：职责边界和阶段匹配，不是详细技术设计。

## 1. 总体职责边界

| 责任主体 | 应承担 | 不应承担 |
|---|---|---|
| 自建运营系统 | CRUD、业务状态、权限、提示词版本、资料引用、审核、幂等、Schema 校验、任务状态、操作记录 | 不把所有外部集成硬编码进同步请求 |
| 自动化平台 | 定时触发、外部 API 编排、通知、低代码集成、非核心批处理、可替换的执行流程 | 不作为业务事实源；不直接写 MySQL；不拥有最终状态机 |
| DeepSeek | 文本生成、资料分析、结构化候选结果 | 不保存业务数据；不决定最终审核状态；不替代 Schema 校验 |
| MySQL | 结构化业务事实、状态、版本、引用、任务元数据和分析结果 | 不由自动化平台绕过后端直接写入 |
| 对象存储 | CSV/TXT 原文件、原始响应、大文件和未来图片/视频/音频 | 不保存需要查询和关联的核心结构化字段 |
| 飞书 | MVP 过渡存储、人工查看、通知和协作 | 不作为长期核心数据库或唯一审核事实源 |

统一调用原则：

```text
自动化平台 → 后端 HTTP API → 校验/幂等/权限 → MySQL / 对象存储
```

平台执行成功不等于业务成功。后端必须返回可追踪的任务 ID、业务记录 ID 或幂等结果。

## 2. 场景总览

| 场景 | 自建系统 | 自动化平台 | DeepSeek | 阶段建议 |
|---|---|---|---|---|
| A 资料手动添加 | 主责 | 不参与 | 不参与 | 一期 |
| B 资料自动采集 | 保存规则与结果 | 定时/外部编排，可选 | 可选后处理 | 一期只做一个合法来源试点 |
| C 资料分析 | 主责版本、引用、校验 | 异步触发可选 | 主责生成 | 一期可用现有 Make；中期后端化 |
| D 选题生成 | 主责业务逻辑 | 过渡触发可选 | 主责生成 | 当前 Make 保留；逐步迁移 |
| E 脚本生成 | 主责关联和版本 | 过渡触发/通知 | 主责生成 | 当前 Make 保留；逐步迁移 |
| F 账号数据采集 | 主责账号授权和数据模型 | 定时/OAuth 刷新可选 | 不参与采集 | 抖音先验证；其他平台文件兜底 |
| G 手动填写数据 | 主责 | 不参与 | 分析阶段才参与 | 一期 |
| H CSV/TXT 导入 | 主责上传、解析、映射和错误展示 | 大批量异步触发可选 | 分析阶段才参与 | 一期先固定模板 |
| I 结构化分析输出 | 主责 Schema、重试和审核 | 异步执行可选 | 主责候选输出 | 一期最小闭环；长期后端主导 |

## 3. 场景 A：资料库手动添加

目标链路：

```text
自建后台表单 → 后端 API → 校验 → MySQL
```

职责判断：

- 自建系统主责字段校验、来源、标签、有效期、审核状态和操作记录；
- 自动化平台不需要参与。简单 CRUD 绕自动化平台会增加失败点、延迟和数据一致性问题；
- DeepSeek 不参与，除非用户显式发起“分析这条资料”。

平台匹配：所有自动化候选均为“不需要”。一期应先把人工资料入口做稳定，而不是强行自动化。

## 4. 场景 B：资料自动采集

目标链路：

```text
定时/手动触发 → 外部 API → 分页 → 保存原始响应 → 清洗 → 去重
→ 后端 API → MySQL → 执行日志
```

职责分配：

- 后端保存采集源配置、游标、水位、幂等键、去重规则和业务状态；
- 自动化平台适合定时触发、分页编排、外部请求、通知和简单转换；
- 复杂签名、反爬、断点续传、大量分页和跨页去重应由可测试的后端代码承担；
- 原始响应可先放对象存储，MySQL 保存摘要、来源、哈希和处理状态。

候选匹配：

| 候选 | 匹配判断 | 适用阶段 |
|---|---|---|
| Make | 当前熟悉；适合低频、少页 API；模块信用和复杂分页是限制 | MVP |
| n8n | HTTP 分页、代码、错误工作流和队列路径明确 | 优先实测 |
| Activepieces | 适合简单采集；复杂并发下官方生产资源较重 | 低频试点 |
| Windmill | 代码、worker、队列和定时强，最适合复杂采集原型 | 中期候选 |
| Node-RED | 简单 HTTP 流程可用；durable retry 和治理需自建 | 小型流程 |
| Pipedream | 托管代码和定时方便；不自托管、按计算信用 | 云端备选 |
| 自建队列 | 幂等、断点、批量和测试最好；开发成本最高 | 长期核心 |

一期建议：只选择一个有官方 API、业务价值明确的资料源做端到端验证，不把网页爬取作为正式方案。

## 5. 场景 C：资料分析

目标链路：

```text
资料版本 + 分析提示词版本 → DeepSeek → JSON 候选结果
→ 后端 Schema 校验 → 人工审核/重试 → MySQL
```

职责分配：

- 后端在任务创建时固化资料版本 ID、提示词版本 ID、模型标识和请求摘要；
- DeepSeek 负责生成，不负责最终结构合法性和业务审核；
- 自动化平台可以承接异步调用、超时重试和通知，但不应保存唯一的提示词或引用关系；
- 分析结果回写资料库前必须标识“AI 分析产物”，防止与原始事实混淆。

DeepSeek 官方 [JSON Output](https://api-docs.deepseek.com/guides/json_mode/) 能保证有效 JSON 字符串，但官方提示仍可能出现空内容或长度截断。因此必须追加：

- JSON Schema 或等价字段校验；
- 缺字段、空内容、截断和类型错误处理；
- 有上限的重试与退避；
- 原始响应保留；
- 人工修正和审核入口。

阶段建议：短期可由 Make/n8n/Activepieces 调 DeepSeek；长期建议后端直接调用，自动化平台只负责触发与通知。

## 6. 场景 D：选题生成

目标链路：

```text
用户输入 + 资料范围快照 + 选题提示词版本
→ DeepSeek 批量生成 → JSON/字段校验 → 去重
→ 后端保存选题、引用和任务 → 人工筛选
```

不能只放在自动化平台的逻辑：

- 资料范围快照和引用关系；
- 提示词版本；
- 同一批次、跨批次和已有选题的重复判断；
- 选题状态和人工筛选；
- 幂等和批量写入事务；
- 生成失败后的任务状态。

平台判断：

- 当前 Make 场景已真实跑通 15 条生成，短期应保留；
- 中期让 Make 调后端“创建生成任务”API，结果写入后端，不再直接写飞书；
- n8n/Activepieces 可替代触发与编排，但不能解决业务去重和追溯；
- 后端直接调用 DeepSeek 最适合长期核心。

## 7. 场景 E：脚本生成

目标链路：

```text
选题版本 + 资料范围快照 + 脚本提示词版本
→ DeepSeek → 保存脚本版本 → 人工修改 → 人工审核
```

职责分配：

- 后端维护选题与脚本的关联、脚本版本、当前稿、修改人、审核人和引用资料；
- 长文本正文可以保存在 MySQL 文本字段；附件和媒体进入对象存储；
- 自动化平台适合生成触发、异步任务、超时重试和完成通知；
- 自动化平台不适合承担多人编辑、版本比较和审核状态机。

阶段建议：当前 Make 脚本场景继续运行；自建后台形成版本和审核能力后，再把写入目标从飞书迁到后端 API。

## 8. 场景 F：账号数据自动采集

### 8.1 官方能力核验

| 平台 | 官方证据 | 当前可确认 | 不能确认/限制 | 一期兜底 |
|---|---|---|---|---|
| 抖音 | [OpenAPI 列表](https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/list)、[特定视频数据](https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/video-management/douyin/search-video/video-data) | 有 OAuth/access_token、粉丝数据、视频基础信息和特定视频实时指标相关 API | 应用类型、scope、审核、账号授权、指标覆盖和配额需真实申请验证 | 手工/CSV |
| 视频号 | [视频号开放文档](https://developers.weixin.qq.com/doc/channels/) | 有视频号助手、直播记录、直播大屏、留资及电商相关 API | 未在公开目录确认普通短视频播放、点赞、评论、转发、粉丝全量分析 API；账号/行业权限待验证 | 视频号助手导出、手工/CSV |
| 小红书 | [电商开放平台 API](https://open.xiaohongshu.com/document/api)、[聚光 Marketing API](https://ad.xiaohongshu.com/openApiDoc?articleId=2777) | 官方开放能力集中在电商和广告数据，聚光 API 有账号及技术门槛 | 未确认普通内容账号笔记播放/曝光、点赞、评论、收藏和粉丝全量 API | 专业号后台导出、手工/CSV |
| 其他平台 | 待姐夫确认平台后再查官方开放平台 | 尚未调研 | 不应提前假设可采集 | 手工/CSV |

### 8.2 采集原则

- 只使用官方 API、正式授权导出或合同允许的数据服务；
- OAuth token、刷新 token 和 scope 由后端安全保存，自动化平台只在必要范围使用；
- 采集任务保存平台、账号、时间窗口、原始响应位置、游标、成功/失败数量和错误原因；
- 播放、点赞、评论、转发、收藏、粉丝等指标必须定义时间口径和累计/增量语义；
- 网页爬取只能列为高风险备选，不作为正式、稳定、合规方案；
- 第三方数据商必须另行核验授权、合同、导出字段和数据使用限制。

### 8.3 平台参与方式

- 抖音 OAuth 和定时拉取可由 n8n/Make/Windmill 触发，但 token 生命周期、scope 和幂等由后端控制；
- 视频号和小红书在官方普通内容指标 API 未确认前，不为它们建设“假自动采集”；
- 首期以手工/CSV 形成可分析数据闭环，比先写不稳定爬虫更有价值。

## 9. 场景 G：手动填写数据

目标链路：

```text
自建后台表单 → 数据校验 → MySQL → 创建分析任务
```

自动化平台不需要参与。后端应提供必填校验、数值范围、日期、账号归属、重复日期和修正记录。录入完成后如需异步分析，再创建任务交给自动化平台或队列。

## 10. 场景 H：CSV/TXT 导入

目标链路：

```text
文件上传 → 对象存储保留原文件 → 后端解析 → 字段映射
→ 校验预览 → 用户确认 → 标准化入库 → 分析任务
```

职责判断：

- 文件上传、字段映射、逐行错误展示、重复处理和确认入库应由后端承担；
- 自动化平台可在入库后触发分析、通知或处理超大异步批次，但不应成为用户看不到的文件解析黑盒；
- 对象存储保存原文件、导入批次和错误文件；MySQL 保存映射配置、标准化记录和错误摘要；
- 一期只支持一个或少数固定模板，先提供“预览后确认”，不承诺任意 CSV/TXT 自动识别。

候选判断：Make/n8n/Activepieces 可做小文件原型；Windmill/后端代码更适合复杂解析；长期维护性以自建后端最高。

## 11. 场景 I：结构化分析输出

目标链路：

```text
分析任务 + 原始数据版本 + 资料上下文 + 提示词版本
→ DeepSeek JSON Output → 解析 → Schema 校验
→ 缺字段/类型错误处理 → 重试或人工修正
→ 审核 → 保存结构化结果 → 可选回写业务库
```

最低要求：

- 每个分析任务有稳定的输出 Schema 版本；
- 字段配置有名称、类型、是否必填、枚举、说明和默认策略；
- 原始响应与解析后结果同时保留；
- 空内容、截断、非法 JSON、合法 JSON 但字段错误分开记录；
- 自动重试有次数上限，不覆盖原失败记录；
- 人工修正产生新版本并记录修正人；
- 审核通过后才能回写资料库、选题库或脚本库；
- 回写内容标明数据来源和 AI 生成属性，避免循环引用。

平台判断：

- n8n、Activepieces 和 Make 可完成 HTTP 调用与 JSON 解析，但业务 Schema、版本和审核仍应在后端；
- Windmill/后端代码更适合复杂校验和批处理；
- 长期最稳妥的是后端直接调用 DeepSeek，队列处理重试，自动化平台只做外围编排。

## 12. 阶段匹配

### 短期

- 手动资料、手动数据、固定 CSV 模板由自建系统负责；
- 当前 Make 的选题和脚本场景保持运行；
- 飞书继续作为过渡查看端；
- 不安装新平台，不修改现有场景，先明确后端 API 契约和业务规则。

### 中期

- 在升级后的 VPS 上最小实测 n8n 单实例，同时测 Activepieces 单容器或 Windmill 中的一项，不并行安装全部平台；
- 自动化平台只调用后端 API，不直接写 MySQL；
- 选择一个抖音官方 API 或合法资料源做采集试点；
- 将 DeepSeek 结构化校验、提示词版本和引用保存放到后端。

### 长期

- 自建系统成为业务事实、状态、权限、版本和审计核心；
- 核心 AI 生成、复杂采集和结构化分析由后端任务队列承担；
- 自动化平台保留在通知、低代码外部集成、临时运营流程和可替换任务；
- 飞书退到通知和协作入口。

## 13. 待确认问题

选型前只需要优先回答三类高影响问题：

1. 姐夫是否需要亲自编辑自动化流程，还是只操作自建后台；
2. 一期最优先的是内容生成、资料采集还是数据分析，以及每日/每周真实任务量；
3. 无官方 API 的平台是否接受手工或 CSV 兜底，允许持续多久。

这些答案会改变非技术易用性、VPS 自托管、开发成本和采集能力的权重。
