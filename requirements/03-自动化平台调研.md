# Forge 新媒体运营系统：自动化平台调研

> 调研日期：2026-08-23
> 调研阶段：第 2 步
> 结论性质：阶段性研究，不是最终安装或迁移决定。

## 1. 调研目标与口径

本轮比较 Make、n8n、Activepieces、Windmill、Node-RED、Pipedream 和自建后端任务调度/队列，回答三个问题：

1. 哪些能力适合短期继续利用，避免重做已经跑通的 MVP；
2. 哪些平台值得在 LisaHost VPS 升级后做最小实测；
3. 哪些业务逻辑必须留在自建后端，避免自动化平台成为新的业务数据库。

证据只采用官方文档、官方定价、官方集成目录和官方项目文档。检索日期为 2026-08-23。价格、版本和套餐能力可能变化，实施前需重新核对。

状态标记：

- **官方已确认**：官方资料直接支持该判断；
- **官方未说明**：公开官方资料没有给出足够信息；
- **需要实际验证**：存在官方能力，但本项目可用性、资源或账号条件必须实测；
- **不适用**：该维度不适用于此候选。

“存在通用 HTTP 请求能力”只表示可以按第三方 API 文档自行接入，不等于平台提供原生 DeepSeek 或飞书连接器。

## 2. 结论摘要

- **Make**：当前 MVP 的保留价值最高，适合短期继续承担已跑通的选题和脚本流程；核心平台由供应商托管，VPS 压力小，但按模块信用计费且长期锁定风险较高。
- **n8n**：自托管、连接器、代码节点和可视化编排最均衡，是优先级最高的 VPS 替代验证对象；生产队列会增加 PostgreSQL、Redis 和 worker，4G 单机不能未经实测直接承诺。
- **Activepieces**：非技术体验和原生 DeepSeek/MySQL Piece 有吸引力；官方推荐生产拓扑包含 App、worker、PostgreSQL、Redis 和 S3，明显超出 4G 单机的舒适余量。
- **Windmill**：适合代码化采集、脚本、定时作业和数据处理；自托管依赖 PostgreSQL 作状态和作业队列，更偏开发者平台，不宜让操盘手直接维护复杂流程。
- **Node-RED**：轻量、开放、Docker 方便，适合设备/事件或小型 HTTP 流程；MySQL 等依赖额外节点，长期队列、审计、权限和业务追溯需要较多自建约束。
- **Pipedream**：托管工作流和代码执行成熟，VPS 无平台负担；公开官方资料没有核心工作流自托管路径，不符合“长期核心尽量落在自有 VPS”的方向。
- **自建后端任务调度/队列**：最适合长期承载业务一致性、提示词版本、资料引用、Schema 校验和幂等；代价是开发、测试、监控和运维成本最高。

## 3. 官方证据

### 3.1 Make

官方证据：

- [Make 定价](https://www.make.com/en/pricing)：Free 为 1,000 credits/月，Core 在 10,000 credits/月档按月 $12，Pro $21，Teams $38；每个模块动作计信用，Make API 从 Core 起提供，团队角色和模板共享在 Teams。
- [Webhooks](https://help.make.com/webhooks)：可通过 HTTPS 接收外部事件，并有 Webhook 队列。
- [Schedule a scenario](https://help.make.com/schedule-a-scenario)：支持场景定时与运行频率控制。
- [Scenario settings](https://help.make.com/scenario-settings)：Webhook 默认可并行处理，也可配置顺序处理。
- [Error handling](https://help.make.com/error-handling)：提供错误处理器和指数退避相关能力。
- [MySQL integrations](https://www.make.com/en/integrations/mysql)：官方集成目录提供 MySQL 连接入口，具体动作和套餐仍需实际账号验证。

判断：Make 是云端视觉工作流产品。公开资料未提供把 Make 核心引擎完整部署到 LisaHost VPS 的方式；任何本地代理能力都不能等同于核心自托管。

对本项目的优势：现有两条链路已真实跑通，短期零迁移成本，操盘手已有简单入口。

主要风险：模块级信用消耗、复杂场景维护、业务状态分散、平台导出后的可移植性有限。DeepSeek 与飞书当前已验证方式均为 HTTP/第三方应用，不应写成 Make 官方原生支持。

### 3.2 n8n

官方证据：

- [Docker 安装](https://docs.n8n.io/deploy/host-n8n/install-options/install-with-docker)：官方推荐多数自托管场景使用 Docker，并明确自托管需要服务器、容器、安全、资源和扩容知识；默认 SQLite，也支持 PostgreSQL。
- [Queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode)：队列模式由主实例、Redis、worker 和数据库组成，官方称其为最佳扩展模式；SQLite 不推荐用于队列模式。
- [Webhook 节点](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook)：支持测试/生产 URL、认证、二进制输入和响应控制。
- [HTTP Request 节点](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest)：支持常用 HTTP 方法、认证、分页、批处理和文件请求。
- [MySQL 节点](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.mysql)：内置查询、插入、更新、删除等操作。
- [DeepSeek Chat Model 节点](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.lmchatdeepseek)：存在官方内置 DeepSeek Chat Model 节点。
- [Source control and environments](https://docs.n8n.io/administer/use-source-control-and-environments)：Git 环境功能属于 Business 和 Enterprise。
- [n8n 定价](https://n8n.io/pricing/)：Cloud 按完整 workflow execution 计费；Community Edition 可自托管。当前 Business 为自托管付费档，Git、环境、SSO 等治理能力并非 Community 全部提供。

判断：n8n 是最均衡的替代验证对象，但“可自托管”不能推导出“无需专业运维”或“全部企业治理免费”。

对本项目的优势：DeepSeek、MySQL、Webhook、HTTP、代码和队列路径明确；可把外部编排部署到自有环境。

主要风险：生产形态可能额外引入 PostgreSQL 和 Redis，与计划中的 MySQL 共存；升级、安全、备份和队列运维由团队负责。

### 3.3 Activepieces

官方证据：

- [Docker 安装](https://www.activepieces.com/docs/install/options/docker) 与 [Production Setup](https://www.activepieces.com/docs/install/configure-operate/production-setup)：支持 Docker；官方推荐生产形态包括 App、worker、PostgreSQL、Redis 和 S3。
- [Workers](https://www.activepieces.com/docs/install/architecture/workers)：worker 从 Redis 获取任务并执行 Flow。
- [生产资源建议](https://www.activepieces.com/docs/install/configure-operate/production-setup)：官方示例按每个并发 Flow 配一个约 0.5 vCPU/1 GB worker，App 约 1 vCPU/1 GB，PostgreSQL 起点约 2 vCPU/4 GB，Redis 约 1 vCPU/1 GB，并把 S3列为生产要求。
- [Activepieces 定价](https://www.activepieces.com/pricing)：提供云端和 on-prem；当前 Free $0、Plus 年付折算 $16/月、Team 年付折算 $166/月，高阶治理为定制价。
- [DeepSeek Piece](https://www.activepieces.com/pieces/deepseek)：官方 Piece 目录提供 DeepSeek 动作和 JSON 响应格式选项。
- [MySQL Piece](https://www.activepieces.com/pieces/mysql)：官方 Piece 提供查询、插入、更新、删除和执行 SQL。

判断：Activepieces 具备良好的可视化和 AI 集成，但官方生产基线不适合直接压进包含 API、MySQL、Nginx 的 4G 单 VPS。

对本项目的优势：DeepSeek/MySQL 原生 Piece 明确；云端与自托管兼有；面向非技术用户的流程体验值得实测。

主要风险：低配单容器只能作为低频试验，不能代表官方生产拓扑；Git Sync、审计、密钥管理等高级治理受套餐限制；未找到官方 Lark/飞书 Piece。

### 3.4 Windmill

官方证据：

- [Self-host](https://www.windmill.dev/docs/advanced/self_host)：小型部署可用 Docker/Docker Compose；核心包含 PostgreSQL、Server、worker、反向代理等，PostgreSQL 保存平台状态和作业队列。
- [Scaling workers](https://www.windmill.dev/docs/advanced/scaling)：worker 从共享队列拉取任务，一次执行一个任务，可横向扩展。
- [Webhooks](https://www.windmill.dev/docs/core_concepts/webhooks)：脚本和 Flow 自动获得同步/异步 Webhook。
- [Schedules](https://www.windmill.dev/docs/core_concepts/scheduling)：支持 CRON 风格定时及错误/恢复处理器。
- [Git sync](https://www.windmill.dev/docs/advanced/git_sync)：支持工作区 Git 同步；Community 在最多 2 用户的工作区可用，完整治理按版本受限。
- [Windmill 定价](https://www.windmill.dev/pricing)：自托管开源版 $0 起；Enterprise 从 $120/月起，审计、SAML、队列指标和高级治理存在版本边界。

判断：Windmill 更像开发者脚本、作业和内部工具平台，而不是面向操盘手直接配置的轻量无代码工具。

对本项目的优势：复杂分页、清洗、代码化采集、定时任务、Webhook、worker 和 Git 追踪能力强。

主要风险：额外 PostgreSQL 和 worker 增加 4G VPS 压力；对开发能力要求高；DeepSeek、飞书和 MySQL 应按脚本/HTTP/资源接入，不写成已确认原生连接器。

### 3.5 Node-RED

官方证据：

- [About Node-RED](https://nodered.org/about/)：Node-RED 是 OpenJS Foundation 下、基于 Node.js 的流式编程工具。
- [Docker](https://nodered.org/docs/getting-started/docker)：支持 Docker、Compose 和 `/data` 持久化。
- [Core nodes](https://nodered.org/docs/user-guide/nodes)：核心包含 Inject、Debug、Function、Change、Switch 等节点；HTTP In/Response 和 HTTP Request 属于常用核心能力。
- [Projects](https://nodered.org/docs/user-guide/projects/)：Projects 使用 Git 管理 Flow 文件。
- [Securing Node-RED](https://nodered.org/docs/user-guide/runtime/securing-node-red)：支持编辑器/API 认证、基础权限和凭据保护配置。
- [node-red-node-mysql](https://flows.nodered.org/node/node-red-node-mysql)：MySQL 节点位于官方 Flow Library，但属于额外安装节点，不是 Node-RED 核心节点。
- [Admin API](https://nodered.org/docs/api/admin/)：提供运行时管理 API。

判断：Node-RED 轻量且可嵌入，但要把它提升为长期业务编排核心，需要自建 durable queue、细粒度权限、审计和执行追溯规范。

对本项目的优势：低资源、Docker 简单、JavaScript Function 灵活、Git Projects 降低纯画布锁定。

主要风险：社区节点质量和升级兼容性需逐个验证；失败重试、并发队列、多环境和协作治理不如专门工作流平台完整。

### 3.6 Pipedream

官方证据：

- [Workflows](https://pipedream.com/docs/workflows)：托管式工作流按触发器和步骤执行，无需用户管理服务器。
- [Triggers](https://pipedream.com/docs/workflows/building-workflows/triggers)：支持 HTTP 和定时触发等。
- [HTTP](https://pipedream.com/docs/workflows/building-workflows/http)：支持预构建动作或通用 HTTP 请求。
- [Handling errors](https://pipedream.com/docs/workflows/building-workflows/errors)：提供步骤错误和工作流错误处理。
- [GitHub Sync](https://pipedream.com/docs/workflows/git)：可把工作流序列化并同步到 GitHub。
- [Pricing](https://pipedream.com/docs/pricing)：Workflow 按计算时间信用计费；官方说明默认 256 MB 下每 30 秒计算时间计一个信用。
- [Virtual Private Clouds](https://pipedream.com/docs/workflows/vpc)：VPC 是 Pipedream 托管的隔离网络，不是把核心引擎部署到 LisaHost VPS。
- [DeepSeek App](https://pipedream.com/apps/deepseek) 与 [MySQL App](https://pipedream.com/apps/mysql)：官方 App 目录页面存在；本轮未登录账号验证具体动作、权限和套餐。

判断：Pipedream 适合减少运维和快速接 API，但公开官方资料未提供核心 Workflow Engine 的 VPS 自托管路径。

对本项目的优势：HTTP、定时、多语言代码步骤、托管执行和 GitHub Sync 完整，VPS 无自动化平台负担。

主要风险：数据和执行依赖云端供应商，按计算信用计费；中国网络和第三方 API 可达性需要实测；DeepSeek/MySQL 官方 App 页面可见但本轮未验证具体动作，飞书原生支持未确认。

### 3.7 自建后端任务调度/队列

这不是单一产品，没有统一官方定价或部署文档。能力取决于后端语言、任务队列、消息代理和运维实现。

官方参考：

- [Celery Introduction](https://docs.celeryq.dev/en/stable/getting-started/introduction.html)：任务通过 broker 分发给 worker，可使用 RabbitMQ 或 Redis 等；worker/客户端有连接失败重试能力。
- [BullMQ retrying jobs](https://docs.bullmq.io/guide/retrying-failing-jobs)：支持失败任务重试、固定/指数退避、并发、去重和调度器等机制。
- [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)：可要求有效 JSON，但官方同时提示可能出现空内容或长度截断。

判断：自建方案能让业务状态、幂等键、提示词版本、资料引用、JSON Schema 校验和审计使用同一套业务语义，但每一项都需要开发和测试，不能把框架能力当成系统已经具备。

对本项目的优势：平台可替换性最高，可直接围绕 MySQL 业务模型和后端 API 设计；无需再维护一个额外 PostgreSQL 工作流数据库。

主要风险：初期开发成本、失败恢复、并发、监控、凭据、升级和安全责任全部由团队承担。

## 6. 不确定项和待验证项

- LisaHost 升级后的真实 CPU、内存、磁盘、Swap、网络和容器限制；
- n8n 单实例与 PostgreSQL/Redis 组合在 4G VPS 上的空闲和峰值占用；
- Activepieces 单容器低频运行能否在非生产拓扑下满足一期稳定性；
- Windmill 与其 PostgreSQL、worker 同机运行时的资源余量；
- Node-RED 的社区 MySQL 节点、重试方案和版本兼容性；
- Pipedream 在中国网络环境调用 DeepSeek、飞书和目标内容平台 API 的延迟与稳定性；
- 各平台飞书原生连接器的当前存在性、覆盖范围和套餐条件；
- Make 场景的真实月运行量、credits、失败率和人工维护时间；
- 操盘手是否需要直接编辑自动化流程；
- 自建后端语言栈、队列实现、监控和运维责任人。
