# 推送模块前端优化 — 迭代需求

> 状态：已确认，待开发
> 日期：2026-08-28
> 背景：飞书推送已上线实测通过。前端为推送骨架期的遗留状态，交互与文案均需更新。

## 问题清单（用户实测反馈）

1. **推送入口埋太深**：推送任务卡片放在报告详情页正文最底部，报告文章很长，用户要滚到底才能创建/查看推送——核心操作应有近路
2. **过时文案误导**（2 处）：
   - 创建弹窗提示条「渠道 API 待实测，创建后发送将返回暂不可用」——后端 501 已替换，推送已可用
   - 推送列表空态「发送能力待实测」——同上
3. **目标人字段语义不清**：表单的「目标人或群」输入框当前仅做记录，实际发送对象来自环境变量 FEISHU_PUSH_OPEN_IDS，用户会误以为填谁发给谁
4. **执行结果反馈弱**：点「发送」后无成功/失败通知弹出，只能盯着列表状态标签刷新看

## 需求

### 1. 推送入口上提（体验主项）

- 报告详情页**头部操作区**（"返回列表/创建推送"按钮那一行）已有「创建推送」按钮 ✅ 保留
- 新增：头部操作区加「**推送任务**」按钮（Badge 显示任务数），点击**滚动定位/抽屉**到推送任务列表——不用滚长文
- 推送任务列表从页尾 Card 改为**侧边抽屉（Drawer）**：从「推送任务」按钮打开，宽度 ~480px，列表+发送按钮+状态全部在抽屉里完成
- 页尾原 Card 移除（避免双入口维护）

### 2. 文案更新

- 弹窗提示条改为：「推送将通过飞书应用发送给配置的接收人」
- 空态改为：「暂无推送任务。已完成报告可创建飞书推送，创建后点发送即推送给接收人。」

### 3. 目标人字段诚实化

- 表单「目标人或群」字段帮助文案改为：「接收人由管理员在系统配置中统一设定（飞书推送接收人），此处填写仅作为备注标识」
- 或者更彻底：该字段改为**只读展示**当前配置的接收人（调后端新接口返回已配置的 open_id 数量/掩码），不允许自由填写——推荐此项，避免用户以为填了就生效
- 后端配合：GET /api/reports/push-config 返回 { channel: "feishu", receivers_count: N }（不返回完整 open_id，脱敏）

### 4. 执行反馈强化

- 点「发送」后：
  - 成功 → message.success('推送成功，接收人已在飞书收到卡片')
  - 失败 → message.error(失败原因摘要)（现有 records[0].error_message 已有数据源）
  - 任务行状态标签实时刷新（现有逻辑保留）

## 边界

- 不改后端推送逻辑（已实测通过）；仅新增 push-config 查询接口
- 不做多渠道（微信）UI 预留

## 验收

1. 报告详情页头部点「推送任务」→ 抽屉打开显示任务列表，全程无需滚动长文
2. 抽屉内创建/发送/看结果闭环，成功有成功提示、失败有原因
3. 创建弹窗无过时文案；目标人字段为只读接收人展示（或诚实备注文案）
4. 长报告页（正文 10 屏以上）验证推送操作全程不触底
